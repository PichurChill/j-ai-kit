# j-can-see 视觉工具使用指南

本 MCP server 提供 9 个视觉/像素工具，用于主模型无多模态输入能力时的看图任务。
工具会根据任务自动编排，但理解下面的选择逻辑能让你（AI）用得更准。

## 触发门控：有眼睛就先用眼睛

工具分两类，触发规则不同：

- **视觉识别类（调上游视觉模型）：`see_image` / `locate` / `inspect` / `ocr_long`** ——
  你有原生视觉输入（能直接 Read/查看图片）时，**默认不要调用**这些工具，直接用自己的眼睛。
  只有以下情况才用：
  1. 用户明确要求用 j-can-see；
  2. 原生视觉失效：图片读不了/报错、返回内容降质到不可用、同一问题原生看不出答案；
  3. 任务超出原生视觉的可靠范围：如两屏以上长图的逐字 OCR（原生读会被降采样丢字）、
     需要可靠坐标而目测明显不可信的场景。
- **本地像素类（不调视觉模型）：`colors` / `image_diff` / `crop` / `trace` / `extract_fg`**
  —— 不受上述门控限制：它们是取像素级真值的仪器（精确 hex、逐像素差异%），任何模型的
  眼睛都给不出这些值，需要时直接用。

不确定自己是否有原生视觉？先试一次原生读图：成功 → 按上面规则走；报错/无图像能力 →
你就是本 server 的目标用户，放心使用视觉识别类工具。

## 工具选择决策树

按你要回答的问题选工具：

| 问题 | 工具 |
|---|---|
| 这张图是什么 / 说了什么？ | `see_image` |
| 多张图各自是什么？（逐图独立识别） | `see_image` + `each: true` |
| 某个东西在哪？（单个目标） | `locate` |
| 所有同类元素在哪？（每类元素） | `inspect` |
| 这张超长截图的文字？ | `ocr_long` |
| 把这块裁出来存成文件 | `crop` |
| 这两张图哪里不同？ | `image_diff` |
| 这里到底是什么颜色？ | `colors` |
| 深背景图里内容/图表的实际色？ | `colors`（`exclude_background: true`，或看自动附带的背景排除视图） |
| 图表/数据可视化的系列色？（柱状图每根柱、折线颜色） | `colors` 窄条 `profile:"y"` 探测 + 单系列 `region` 取值（见 playbook 7） |
| 上下/左右颜色是否一致？渐变哪里断了？ | `colors`（`profile` / 双 `region` 对比） |
| 这个图形的矢量形状？ | `trace` |
| 把这个图标抠成透明 PNG | `extract_fg` |

## 核心原则：不信任文字描述的像素级事实

视觉模型对**颜色、尺寸、坐标**的描述是模糊的（"浅灰"、"大概在右上"）。
凡是要写进代码的像素级事实，**用本地工具取真值**：

- 颜色 → `colors`（返回精确 hex + 候选色匹配）
- 差异 → `image_diff`（逐像素比较）
- 矢量 → `trace`（从像素拟合 SVG）

这些工具本身也有边界，用之前先知道：

- `colors` 按 5 位量化分桶聚类 + **近邻簇后合并**（Δ≤8）：UI 纯色精确，
  渐变会收敛为少量「渐变簇」（起止色见 profile），占比恢复参考价值。
  要精确取某处的色，先用 `region` 把范围缩到那一块；
  **深色仪表盘/大背景图**会淹没主色榜 —— top1 占比 >60% 时输出自动附
  「背景排除视图」（四角采样推测背景），也可直接传 `exclude_background: true`
  以排除视图为主；**比较两处颜色**就并行发两次 `colors`（各带一个 `region`）比主色 hex；
  **要看颜色的空间结构**（渐变段 / 接缝 / 断层在哪）用 `profile: "y" | "x"`，
  它返回均匀段（纯色/渐变）与跳变点的位置和两侧色值。
- `image_diff` 返回的是 12×12 网格里差异密度最高的**格子**，不是精确包围盒 ——
  一处跨格线的改动会报成好几块。它用来回答"去哪儿看"，不是"改动的确切边界"。
- `trace` 只适合扁平高对比图形；照片和复杂渐变出来的 SVG 没有使用价值。
- **放大不增加信息**：`crop` 放大超过原始分辨率的区域时，模型看到的是插值伪影
  —— 小尺寸渐变放大后会出现真实的同心圆环带，模型数的"纹理圈数/圆环"可能是在
  数伪影，不是原图内容。给模型看的放大 **≤2-3 倍足够**；要精确颜色/纹理，用
  `colors` + `region` 在原图上取（不经过发给模型的 JPEG 编码，色值不受压缩影响）。

## 核心工作流：粗到细

多步看图任务遵循「先全局，后局部」：

```
inspect（扫整体布局，拿到所有元素的坐标）
  → locate（锁定你关注的具体目标，拿精确坐标）
    → see_image（用 region 放大看那个目标的细节）
```

坐标在工具间是通用的（原图像素）：`locate`/`inspect` 返回的 `x1,y1,x2,y2`
直接作为 `see_image`/`crop` 的 `region` 参数传入即可。

`locate`/`inspect` 自身也接受 `region`（先裁剪再定位/盘点，输出仍换算回整图坐标）——
长图上的小目标、密集屏幕的分区盘点、locate 失败后的「缩小范围重试」都走这条路，
不必先 crop 存文件。

## 场景 playbook

### 1. UI 设计稿还原

1. `inspect` 盘点所有 UI 元素（按钮/输入框/图标）→ 拿到布局坐标
2. 对关键区域 `colors` 取精确色值（别信"浅蓝"）
3. `see_image` + `region` 看小图标/文字细节
4. 需要的图标用 `extract_fg` 抠成透明 PNG 复用
5. 写代码后，截图与设计稿 `image_diff` 对齐，差异区 `see_image` 复核

### 2. GUI 自动化（看图操作）

1. `locate` 定位目标控件（如"发送按钮"）→ 拿坐标
2. 执行点击/输入（用其他工具，坐标已拿到）
3. 重新截图，`image_diff` 与操作前对比，或 `see_image` 确认状态变化

### 3. 长截图 / 长聊天记录 OCR

- **不要**用 `see_image` 一次性 OCR 超长图（服务端降采样会丢字）
- 直接用 `ocr_long`：自动优先在低内容带（空白/稀疏行）切口 —— 安全切口
  两侧无重叠、无去重负担；密集内容找不到安全切口才退回重叠区兜底防丢字
- 它会保留发言人 / 时间戳 / 引用结构
- 图太高（超过 16 块）会直接报错并要求先用 `crop` 纵向切段——照做，别硬试

**必须读边界审计**。`ocr_long` 会逐条报告每个分块边界的处理结果，三种都要当回事：

- `安全切口（低内容带，无重叠，未做去重）` —— 切在空白带上，无风险
- `⚠️ 未能识别重叠内容` —— 该处**可能有重复文字**。通常是那一行正好被切断、
  两侧转录不一致所致。用 `see_image` + `region` 复核它给出的 y 区间，
  再决定要不要手工删重复。
- `去除重复 N 行：「...」` —— 这些行被删掉了。若原文本来就有连续重复
  （聊天记录里连发两条一样的消息），那就是**误删**，同样用 region 复核。

去重是保守的（只在首尾行完全一致时才删），所以「漏删」比「误删」常见。
转录结果要用于正式用途时，把审计提到的边界都复核一遍。

### 4. 图形 / 图标矢量化

- 线框图、流程图、手绘草图、简单图标 → `trace` 转 SVG
- **照片、复杂渐变、阴影丰富的图不要用 trace**（矢量化效果差，这是算法本质）
- 需要可复用图标素材 → `extract_fg` 抠透明 PNG

### 5. 实现截图 vs 设计稿对比

**对比单位是组件，不是整页**：整页截图里目标组件只占一小块像素，模型看不清布局
细节（实测会得出"上下两行 vs 同一行"这类矛盾结论）。先定位组件，再在组件级
局部图上对比。每轮「改代码 → 截图 → 对比」循环按此流程：

1. **截图规范**：实现图与设计稿用同一视口尺寸、同一滚动位置截（如 430×900），
   否则任何对比都会被视口差异污染
2. **归一化尺寸**：两图尺寸不一致时逐像素比全是噪声。`image_diff` 会自动对齐
   到面积较小者（坐标以该图为准）——直接比即可，无需手工预处理；也可用
   `crop(0,0,宽,高, scale: 目标宽/当前宽)` 手工缩放（scale 支持 <1 缩小）
3. **`image_diff` 定位 + 收敛度量**：差异% 是天然回归指标——改代码后差异应下降，
   降到阈值内即完成，别靠模型目测"像不像"；返回的差异区域坐标以基准图
   （面积较小者）为准，**回喂 region/crop 时用基准图作为 source**
4. **组件级多图对比**：把实现图与设计稿的组件区各自 `crop` 出来（放大到能看清
   细节的尺寸），`see_image([impl, design], "Compare these two components item by item: layout, values, colors, font sizes, spacing. List every difference. Answer in Chinese.")`
   —— 多图模式两张图都保持全分辨率，一次上游调用完成语义对比
5. **细节复核**：对差异清单里的可疑点，`see_image` + `region` 放大确认

多图对比的返回坐标是各自原图坐标，可直接回喂 region。不要自己拼合成一张图再比
—— 合成会把每张图的分辨率砍半（长边 1568 两张拼一张，每张只剩 ~784px），
细节全丢且坐标失效；多图模式已具备"同时看到两图"的能力且无此代价。

### 6. 细微色差 / 渐变检测

「上下两块背景是不是不一样」「渐变是不是断在中间」这类问题，视觉模型对细微色差
（亮度差 ≲5%）**系统性失明**——它说「均匀、没差异」不构成证据。标准流程：

1. **并行开场**：`see_image`（拿语义/布局）+ `colors`（拿主色）一次发出。
   colors 返回多个相近簇（输出会附 ⚠ 相近簇提示）而视觉说「均匀」时，**信 colors**。
2. **结构验证用本地工具，不要再问视觉**：`colors` + `profile: "y"`（或 `"x"`）返回
   颜色沿纵/横轴的剖面——均匀段（起止色、纯色还是渐变）与跳变点（位置、两侧 hex、
   Δ值）。「渐变被平铺/重复」「中途有接缝」这类结论直接由跳变点得出，不需要写脚本
   逐行采样。
3. **只比两处颜色**：两次 `colors` 各带不同 `region` 并行发，比主色 hex 即可。
4. **同一差异问视觉一次就够**：视觉已答「看不出」后，再裁放大图问第二次不会得到
   新信息（放大本身也不增加信息，见上）——直接落本地像素手段（`colors` 的
   region/profile）。

### 7. 图表 / 数据可视化取色（柱状图系列色、折线颜色、对标截图改代码配色）

「把代码里的图表颜色改成和截图一致」这类任务的正确路径是**全程本地像素工具**，
一次视觉调用都不需要（视觉只能给「蓝色渐变」这种定性描述，给不了 hex）：

1. **候选色先从代码拿**：图例/主题配置里通常已有现成色值（如 `#4da3ff`、`#6fe2ff`），
   直接作为 `colors` 的 `candidates` 逐像素验证，比从图上反推再对代码快得多。
2. **探测系列色位置**：对穿过图表主体的**窄条**（20-40px 宽）做
   `colors` + `profile: "y"` —— 返回的渐变段就是各个系列色的垂直分布
   （堆叠柱各段的起止 hex 与边界 y 坐标一次拿全）。
   **方向规则：扫描方向必须垂直于颜色变化方向**——柱色纵向渐变就沿 y 扫；
   横向渐变（条形图）用 `profile: "x"`。方向错了每条线都是杂线，输出为空段。
3. **深背景先排除**：仪表盘深底会淹没主色榜 —— `exclude_background: true`
   （或看输出自动附的背景排除视图）。
4. **单系列精确取值**：用第 2 步拿到的 x/y 坐标圈出单根柱子的 `region`，
   `colors` + `region` + `profile: "y"` 取该柱渐变的起止 hex；写进代码的就是这两个值
   （顶/底色）而不是单一 hex。
5. **验证**：改完代码截图，与参考图 `image_diff`；差异集中在柱区属正常
   （渲染器渐变插值不同），色值本身以第 4 步像素值为准。

## 速度与容错（上游慢 / 限流 / 不稳定时）

视觉调用统一经过服务端全局并发池（自动降档、自动退避重试、超时自动降质），
你不需要也**不应该**自行控制并发或写重试逻辑。要点：

- **多张独立识图用 `each: true` 一次发**，不要并行发多个单图调用 ——
  批量模式在总预算内自动排队并发，做完几张返回几张，永不整单失败。
  并行发 N 个单图调用会在上游拥挤时集体撞客户端超时。
- **续调到清空即任务完成**：批量返回若含「未处理」清单，把返回里给出的
  续调参数原样再调一次，重复直到清单清空。单张失败会记录原因并跳过，
  不影响其他图；看到「连续失败、上游当前不可用」警告时，先干别的活稍后再续调。
- **粗看传小 `max_edge`**：只需判断"这是什么页面/大概布局"时传 `max_edge: 512`，
  耗时显著下降；要读小字或精确细节时用默认（1568）。显式传了 `max_edge`
  的调用超时后不会自动降质（视为你已明确精度意图）。
- **能一步拿全的 `inspect` 优先**：要多个元素的位置+文字时，一次 `inspect`
  优于 locate + see_image 串行多连 —— 少一次上游调用就少 30-90s。
- **读懂降质注脚**：返回末尾出现「已降质（长边 1024px）」说明该结果因超时或
  预算不足以降质图产出 —— 内容可用，但小字与坐标精度打折。需要精确值时：
  对该图用默认分辨率重看一次，或改用本地工具（`colors` 取色、`crop` 放大）。
- **两种失败语义是刻意区分的**：`each` 批量单张失败跳过继续（图彼此独立）；
  `ocr_long` 遇真实故障整单 fail fast（块同属一张图，上游挂了拼出来也是残文）。

## 通用规则

- **落盘文件分两类，路径即意图**：
  - **中间产物**（分析用局部图、临时放大等，用完即弃）→ 统一放项目 `.j-can-see/<任务名>/` 子目录；首次创建时顺手把 `.j-can-see/` 加进项目 `.gitignore`；**任务结束删除**不再需要的文件
  - **不在具体项目内时**（工作目录不是某个项目，如临时任务）→ 中间产物放系统临时目录的 `j-can-see/<任务名>/`（macOS/Linux：`/tmp/j-can-see/<任务名>/`；Windows：`%TEMP%\j-can-see\<任务名>\`），任务结束同样清理；**不要自创新的临时目录**
  - **交付物**（要保留的素材、logo、SVG）→ 显式写到项目正式位置（如 `assets/`）
  - 输出目录不存在会自动创建；相对路径相对 server 工作目录（通常是项目根），不确定时用绝对路径
- **超长图先分段再 OCR**：高于约两屏（≈3000px）的图，`ocr_long` 受总时间预算（默认 85s）约束，预算耗尽只返回已完成部分。拿到"未处理块 y 区间"提示时，用 `crop` 逐段裁出后单独 `ocr_long` 补齐——单块调用能在客户端超时内完成
- **locate/inspect 依赖模型定位能力（grounding）**：模型定位弱时 locate 可能频繁 NOT_FOUND（返回文案会附建议）。长图上定位先 `crop` 局部化或直接用 `region` 参数；仍找不到改用 `inspect` 枚举全部元素
- **locate 找的是「元素」，不是「背景」也不是「图表系列」**：大块纯色背景、柱状图的柱子/折线/系列色块都不是 grounding 模型认得的对象（实测直接 NOT_FOUND）。取色/定位色块改用 `colors`（`region` / `profile` / `exclude_background`）做像素级探测，或用 `inspect` 找到的邻近元素反推
- **细节缺失时自己看**：如果只有文字描述但文件路径可用，用 `see_image`/`locate` 自己看，别猜
- **看图提问规范**：描述类问题用开放式提问（"Describe the center region"），不要
  引导式提问（"Are there ring lines?" 会诱导模型确认"有"）。模型输出里出现「大概/
  左右/类似/可能」这类措辞就是不确定信号——凡是要写进代码的颜色/尺寸/数量，先用
  本地工具复核再采信，不要直接抄进代码
- **给视觉模型的 prompt 一律用英文写**：视觉模型对英文指令的遵循更稳（尤其中文
  偏弱的上游）；需要中文输出时在 prompt 末尾显式说明（如 "answer in Chinese"）
- **工具缺失要说明**：某工具调用失败时如实上报原因，不要编造内容
- **`source` 格式**：本地路径（支持 `~`）/ `http(s)` URL / `"latest"`（最新截图）/ `"clipboard"`（剪贴板，仅 mac/win）
